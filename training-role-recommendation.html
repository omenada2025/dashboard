Training role guide

Training is live in the dashboard as a Functional responsibility (same pattern as UI/UX), with its own lifecycle: Prepare → Deliver → Adopt → Handoff / Support. It is not an access profile.

1. Where Training fits

Keep a clear separation between functional responsibility, access profile, and lifecycle phase.

System layer Use for Training? Why
Functional responsibility Yes — primary pattern Same as UI/UX: who executes post-delivery enablement and reports in Update Reports / Governance.
Access profile (admin / master / roles / executive) No Access profiles control what a person can see and approve. Training is not a system permission.
Lifecycle phase after Release / Learn Only if no Training person Useful when the same Owner (Product Manager) runs enablement without a dedicated Training contributor.
Operational stage (Release, Training, Completed…) Complementary Stage describes portfolio/operational state; lifecycle describes the governance phase of the workstream.

Phase Objective Minimum evidence
1. Prepare Define audience, curriculum, materials, environment, and success criteria. Training plan, participant list, deck/guide.
2. Deliver Run sessions and record coverage. Agenda, notes, attendance, recording.
3. Adopt Measure whether the audience can operate the product. Quiz, shadowing, support tickets, % active users.
4. Handoff / Support Transfer to ongoing operations and close the workstream. Runbook, support contacts, gate Approved + status Delivered.

Product path
Discover → … → Validate → Release / Learn
Delivery and release learning. Does not replace structured enablement.

Training path (live)
Prepare → Deliver → Adopt → Handoff / Support
Post-delivery workstream focused on knowledge transfer and adoption.

4. Owner, weekly updates, and gates

Area How Training connects
Weekly Updates Role / Functional responsibility = Training; lifecycle_phase from the Training path; Owner = who is accountable for that workstream (Training contributor or PM).
Owner model Keep Product Manager as the accountable Owner of the product. Training follows the UI/UX pattern: contributing role. If the workstream is enablement-only, the Training person can be Owner of that workstream.
Product Governance Same fields: classification, evidence_status, evidence_reference, gate_status. Gate Approved only with Validated evidence (for example attendance + materials + adoption criteria).
Evidence / gates Typical evidence: plan, materials, attendance, feedback, competence checklist, adoption metric. Gates: Ready for Review → Approved before advancing phase.
Classifications Reuse Enhancement / Investigation / Gap in the current MVP. Optional later: Enablement or Training Gap — only if the team classifies enablement often.

Ownership rule: Product Manager remains the accountable Owner responsibility in the current model. Training, like UI/UX, contributes and reports; it does not redefine who “is” the product Owner — except for workstreams whose only scope is enablement.

6. Design choices (for context)

Option When it applies Note
A — Training role + own lifecycle Dedicated post-delivery person/team Shipped — mirrors UI/UX
B — Extend product lifecycle after Release / Learn Same Product Manager runs enablement Lighter; no separate role
C — Operational stage “Training” only Portfolio status label only Weak for evidence/gate
D — Access profile “training” Never for this case Confuses permission with responsibility

Shipped default: option A (role + four phases). Use operational stage Training when portfolio visibility helps. If almost nobody selects Training later, the team can lean on product-path enablement without losing evidence/gate fields.

How to use it this week

  • In Status Center, set Role to Training for enablement workstreams.
  • Pick the matching lifecycle phase: Prepare, Deliver, Adopt, or Handoff / Support.
  • Attach attendance, materials, or adoption evidence before requesting an Approved gate.
  • Keep Product Manager as the accountable product Owner unless the workstream is enablement-only.
