Como adicionar Training ao dashboard

Sugestão de encaixe: Training como Functional responsibility (como UI/UX), com lifecycle próprio Prepare → Deliver → Adopt → Handoff / Support — não como access profile.

Veredito: trate Training como nova Functional responsibility (como UI/UX), com lifecycle próprio Prepare → Deliver → Adopt → Handoff / Support. Não crie access profile. Use stage operacional “Training” só como complemento visual no portfólio.

1. Onde Training se encaixa

Separação clara entre responsabilidade funcional, perfil de acesso e fase de lifecycle.

Camada do sistema Usar para Training? Por quê
Functional responsibility Sim — padrão principal Como UI/UX: quem executa o trabalho pós-entrega e reporta no Update Reports / Governance.
Access profile (admin / master / roles / executive) Não Perfil controla o que a pessoa vê e pode aprovar. Training não é permissão de sistema.
Lifecycle phase após Release / Learn Só se não houver pessoa de Training Útil quando o mesmo Owner (PM/SA) conduz a capacitação sem papel dedicado.
Operational stage (Release, Completed…) Complementar Stage descreve o estado operacional do produto; lifecycle descreve a fase de governança do workstream.

Fase Objetivo Evidência mínima
1. Prepare Definir audiência, currículo, materiais, ambiente e critérios de sucesso. Plano de treinamento, lista de participantes, deck/guia.
2. Deliver Conduzir sessões e registrar cobertura. Agenda, ata, lista de presença, gravação.
3. Adopt Medir se o público consegue operar o produto. Quiz, shadowing, tickets de dúvidas, % usuários ativos.
4. Handoff / Support Transferir para operação contínua e fechar o workstream. Runbook, contatos de suporte, gate Approved + status Delivered.

Product path (hoje)
Discover → … → Validate → Release / Learn
Entrega e aprendizado do release. Não substitui capacitação estruturada.

Training path (proposto)
Prepare → Deliver → Adopt → Handoff / Support
Workstream pós-entrega focado em transferência de conhecimento e adoção.

4. Owner, weekly updates e gates

Área Como Training se conecta
Weekly Updates role / Functional responsibility = Training; lifecycle_phase do path Training; Owner = quem responde pelo workstream (pode ser a pessoa de Training ou o PM).
Owner model Manter PM/SA como Owner accountable do produto. Training segue o padrão UI/UX: papel contribuinte. Se o workstream for só capacitação, a pessoa de Training pode ser Owner daquele workstream.
Product Governance Mesmos campos: classification, evidence_status, evidence_reference, gate_status. Gate Approved só com evidência Validated (ex.: presença + material + critério de adoção).
Evidence / gates Evidências típicas: plano, materiais, presença, feedback, checklist de competência, métrica de adoção. Gates: Ready for Review → Approved antes de mudar de fase.
Classifications Reutilizar Enhancement / Investigation / Gap no MVP. Opcional depois: Enablement ou Training Gap — só se o time classificar capacitação com frequência.

Regra de ownership: Product Manager e System Analyst continuam sendo a responsabilidade accountable de Owner no modelo atual. Training, como UI/UX, contribui e reporta; não redefine quem “é” o Owner do produto — salvo workstreams cujo único escopo seja capacitação.

5. Superfície mínima de implementação

Somente recomendação — sem implementar agora. Mudanças aditivas, sem migração destrutiva.

Onde Mudança
FUNCTIONAL_ROLE_OPTIONS Adicionar "Training".
TRAINING_LIFECYCLE_PHASE_OPTIONS Novo array: Prepare, Deliver, Adopt, Handoff / Support.
lifecycleOptionsForRole() Se role === Training → path Training; senão manter UI/UX vs Product.
LIFECYCLE_PHASE_OPTIONS União automática dos três paths (já existe via Set).
Forms / filtros Dropdown Role em Update Reports, Functional responsibility em Governance, filtros Role no Executive/Dashboard.
Docs PRODUCT_GOVERNANCE_GUIDE, USER_MANUAL, product-governance-module-manual, manual.html.
Stages (opcional) Adicionar "Training" entre Release e Completed na lista operacional de stage.
Artifacts (opcional) 1–3 itens no checklist: Training Plan, Attendance Record, Adoption Evidence.
Migração de dados Aditiva: relatórios antigos intactos; sem backfill obrigatório.

6. Alternativas

Opção Quando usar Nota
A — Papel Training + lifecycle próprio Há pessoa/equipe dedicada pós-entrega Recomendado — espelha UI/UX
B — Estender product lifecycle após Release / Learn Mesmo PM/SA faz a capacitação Mais leve; sem novo papel
C — Só stage operacional "Training" Só precisa de status de portfólio Fraco para evidência/gate
D — Access profile "training" Nunca para este caso Confunde permissão com responsabilidade

Se Training for só um estágio após Release: alternativa B estende o product lifecycle com Prepare Training → Deliver Training → Adopt / Support depois de Release / Learn. Serve quando não há papel dedicado, mas perde filtros/coaching por função “Training” e mistura capacitação no path de entrega.

Híbrido pragmático: começar com A (papel + 4 fases). Se quase ninguém selecionar Training, recolher para B sem perder evidência/gate — só o seletor de role.

Próximo passo

  • Validar com o time se existe Owner/Participante dedicado de Training.
  • Se sim, implementar a opção A no dropdown e nos manuais.
  • Se não, considerar a alternativa B (estender product lifecycle) sem novo papel.
