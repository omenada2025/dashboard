Recommendation: add QA as a Functional responsibility

Mirror the Training / UI/UX pattern for dedicated quality work — do not create a “Blocker” or “Risk Manager” role. Blockers and risks stay shared weekly fields; QA owns the validation path that surfaces them with evidence.

Recommendation: add QA as a Functional responsibility with lifecycle Plan → Execute → Validate → Sign-off. Product Manager remains accountable Owner. QA contributes validation, defects, and release readiness — the same ownership model as UI/UX and Training.

Do not add: a Functional responsibility named Blocker, Risk, or Escalation. Those are report/governance signals already covered by blocker text, health, delay reason, Incidents & Delays, and governance classification Risk.

1. Why QA — not a “blocker role”

Option Fit? Why
QA as Functional responsibility Recommended There are dedicated people who test, log findings, and gate release quality. They need a role + lifecycle like Training.
“Blocker / Risk” Functional responsibility No Blocker/risk is a signal every role already reports. A role for “pointing out risk” breaks coaching filters and has no coherent lifecycle.
Only strengthen report quality rules Complement Useful for all roles (require blocker + next action when At Risk) — does not replace QA ownership of validation workstreams.
Access profile for QA No Access profiles control pages/permissions. QA is work responsibility, not a login permission tier.

2. Naming and place in the model

Active today: Product Manager, UI/UX, Training. Proposed next: QA.

Layer Use for QA? Detail
Functional responsibility Yes Who executes test / validation workstreams and reports weekly.
Lifecycle path Yes Plan → Execute → Validate → Sign-off (role-specific, like Training).
Operational stage (QA, QA Review…) Keep Already exists as portfolio stage. Complements lifecycle; do not replace Functional role with stage alone.
Weekly blocker / health / delay fields Shared QA uses the same fields as PM/UI/UX/Training to surface findings. No new “risk-only” role.
Governance classification Risk / Bug / Usability Issue Reuse Formal control items for defects and risks with evidence + gate.

3. Proposed QA lifecycle

Same mechanism as UI/UX and Training: choose Functional responsibility first; Lifecycle phase list switches.

1. Plan

Scope, environments, cases, entry criteria, owners.

→
2. Execute

Run tests, log defects, track blockers and coverage.

→
3. Validate

Retest, regression, acceptance evidence, risk residual.

→
4. Sign-off

Release readiness decision with validated evidence.

Phase Typical evidence Blocker / risk habit
Plan Test plan, environment readiness, case list Flag missing env / data / build as dependency + blocker early.
Execute Execution log, open defects, coverage % Every critical defect becomes blocker text + next action + action owner.
Validate Retest results, regression pack, stakeholder acceptance notes Health At Risk until residual risk is accepted or fixed.
Sign-off Sign-off note, gate Approved, evidence Validated Gate Approved only with Validated evidence (same governance rule).

4. Ownership, weekly reports, and gates

Area How QA connects
Weekly Updates role = QA; lifecycle from QA path; same summary / win / blocker / next action / health fields as other roles.
Owner Product Manager remains accountable Owner of the product. QA is the contributor for validation workstreams (same pattern as UI/UX and Training). For a pure QA workstream, the QA person can be Owner of that workstream.
Governance Use Bug, Risk, Usability Issue, Investigation as needed. Evidence + gate unchanged.
Portfolio stage Keep existing stages QA / QA Review as operational labels; Functional role drives coaching and lifecycle filters.

Ownership rule: do not invent a parallel “risk owner” role. Whoever finds the issue (often QA) reports it; Product Manager stays accountable for product decisions; corrective action owner is named on the report.

Optional complement (any role): quality rule — if Health is At Risk or Major Delay, require blocker + next action + action owner before save. That improves signal quality without a new role.

6. Alternatives (weaker)

  • Stage-only QA — keep using stage “QA” without Functional role. Cheap, but loses filters, coaching, and lifecycle for QA people (same weakness Training avoided).
  • PM owns all testing — no QA role; PM reports validation under Validate / Build. Fine only if there is no dedicated QA capacity.
  • “Risk” role — rejected: duplicates Incidents, Action Items, and Risk classification without a real work path.

Suggested decision

  1. Confirm there are dedicated QA people who should report under their own Functional responsibility.
  2. Approve QA + Plan → Execute → Validate → Sign-off (same pattern as Training).
  3. Keep blocker/risk as shared fields; optionally tighten save rules for At Risk reports.
  4. Implement in app + migration + manuals when ready.
